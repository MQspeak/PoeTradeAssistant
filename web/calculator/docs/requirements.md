# POE2 套利工具需求说明

## 1. 范围说明

本文档基于当前仓库真实状态整理需求，分为两层：

- `当前已实现需求`：代码中已经存在并可验证的能力
- `建议收敛需求`：为解决双实现并存问题而新增的工程化需求

## 2. 当前已实现功能需求

### FR-001 物品主数据维护

- 系统应允许用户新增、编辑、删除物品
- 物品应至少包含 `名称`、`分类`、`金币成本`
- 分类至少支持 `currency` 与 `target`
- 当全部物品被删除时，系统应自动保留一条空记录

### FR-002 基础交易对维护

- 系统应允许用户新增、编辑、删除基础交易对
- 每条交易对应包含 `baseItemId`、`quoteItemId`、`rate`
- 当全部交易对被删除时，系统应自动保留一条空记录

### FR-003 套利标的维护

- 系统应允许用户维护目标物品及其多币种价格
- 目标物品收益计算应复用已有币种与汇率数据

### FR-004 符文套利计算

- 系统应支持维护符文相关成本项
- 系统应支持录入小符文与完美符文价格
- 系统应输出收益率、纯利润、总成本
- 系统应支持金币效率计算
- 系统应在缺失汇率时给出明确提示

### FR-005 公式套利编辑与保存

- 系统应支持编辑一条公式套利草稿
- 草稿应包含 `名称`、`成本项列表`、`收益项列表`
- 每条项目应包含 `名称`、`币种`、`单价`、`单个金币消耗`、`数量`
- 成本项和收益项应支持新增和删除
- 删除到最后一条时，系统应自动保留一条空项目
- 单侧项目数量上限应为 10 条

### FR-006 公式套利结算规则

- 系统应使用第一条收益项的币种作为结算币种
- 系统应将所有成本项和收益项折算到统一结算币种
- 如果缺失某条换算路径，系统应提示缺失的基础交易对
- 系统应输出总成本、总收益、纯利润、收益率
- 系统应在存在 D 币种及其汇率时计算金币效率

### FR-007 公式保存与复用

- 系统应允许保存公式到已保存列表
- 系统应允许从列表载入已保存公式继续编辑
- 已保存列表的收益率、纯利润、金币效率应基于当前汇率实时刷新

### FR-008 三角套利计算

- 系统应支持三条兑换路径输入
- 每条路径应包含 `输入币种`、`输出币种`、`汇率`、`手续费比例`、`固定手续费`
- 系统应校验三跳路径首尾闭环
- 系统应输出净利润、ROI、闭环倍率、第三跳保本汇率和每跳明细

### FR-009 本地存储

- 系统应将用户输入保存到 `localStorage`
- 刷新后应自动回填已保存状态

## 3. 非功能需求

### NFR-001 本地可运行

- 用户应可直接双击本地文件运行主工具
- 不应依赖后端服务

### NFR-002 实时反馈

- 用户修改输入后，结果应立即重算
- 不应要求手工点击“计算”按钮

### NFR-003 可读性

- 页面应明确区分成本、收益、利润、效率等关键指标
- 缺失数据时应返回可理解的中文提示

### NFR-004 容错性

- 非法数字、缺失币种、缺失汇率时，系统不应崩溃
- 系统应返回不完整或缺失汇率提示

### NFR-005 可维护性

- 状态模型、计算逻辑、页面渲染不应继续无边界膨胀
- 关键业务规则应可被自动化测试覆盖

## 4. 建议新增的收敛需求

### CR-001 唯一运行入口

- 项目必须明确唯一用户入口
- `启动套利工具.cmd`、开发入口、构建入口应指向同一实现

### CR-002 唯一源码事实来源

- 项目必须明确是以单文件版本为主，还是以 React 版本为主
- 不允许两套实现长期并行承载不同功能

### CR-003 唯一测试对象

- 自动化测试必须覆盖唯一主实现
- 不应出现“测试覆盖 A，实现构建 B，用户使用 C”的状态

### CR-004 文档化交付规范

- 必须补充启动方式、构建方式、发布方式说明
- 必须说明本地数据存储位置与兼容策略

## 5. 验收标准

- 单文件主工具能正常打开并通过现有脚本测试
- `npm run build` 能成功生成产物
- 文档能明确解释当前双实现状态
- 后续重构前，团队能基于本文档达成“保留哪套实现”的共识
