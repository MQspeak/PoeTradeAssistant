# POE2 套利工具任务拆分

## 目标

将当前“双实现并存、入口分裂”的项目收敛成一套可持续维护的本地套利工具，并确保现有业务能力不丢失。

## Phase 1. 基线固定

- [ ] 确认主实现方向：单文件版优先，或 React/Vite 优先
- [ ] 确认唯一用户入口
- [ ] 确认唯一构建发布链
- [ ] 在 README 或交付文档中写明当前启动方式、构建方式、测试方式
- [ ] 盘点单文件版已有能力，形成迁移清单

交付结果：

- 团队对“哪套实现是主线”达成一致
- 后续开发不再继续向两套实现同时加功能

## Phase 2. 业务能力映射

- [ ] 将单文件版全部分页能力列成能力矩阵
- [ ] 将 React 版现有能力列成能力矩阵
- [ ] 标记能力差异：物品列表、交易对、套利标的、符文套利、公式套利
- [ ] 标记公共业务规则：汇率换算、金币效率、错误提示、本地存储
- [ ] 标记重复逻辑与不可复用逻辑

交付结果：

- 得到一份“现状能力差异表”
- 为后续迁移或收敛提供边界

## Phase 3. 架构收敛

如果选择 React/Vite 作为主实现：

- [ ] 抽离单文件版的公共计算逻辑
- [ ] 在 React 中建立统一的领域模型与类型定义
- [ ] 迁移物品列表页面
- [ ] 迁移基础交易对页面
- [ ] 迁移套利标的页面
- [ ] 迁移符文套利页面
- [ ] 迁移公式套利页面
- [ ] 用 React 入口替换当前用户启动入口

如果选择单文件版作为主实现：

- [ ] 将内联脚本拆分为独立模块
- [ ] 将状态、计算、渲染、事件处理分层
- [ ] 降低 `index.html` 体积与耦合度
- [ ] 明确最终打包方式
- [ ] 删除或冻结 React 旁路线

交付结果：

- 形成唯一主实现
- 用户入口、源码入口、构建入口一致

## Phase 4. 测试补强

- [ ] 为唯一主实现建立真实可执行的测试策略
- [ ] 保留现有关键业务规则测试
- [ ] 为汇率缺失、币种缺失、非法输入补充测试
- [ ] 为公式套利的保存、加载、编辑补充测试
- [ ] 为符文套利关键计算补充测试
- [ ] 为三角套利闭环校验补充测试
- [ ] 将测试命令统一到 `package.json`

交付结果：

- 测试覆盖真实交付物
- 不再出现“测的是 A，发的是 B”

## Phase 5. 发布与运维整理

- [ ] 确认最终产物是根目录 HTML 还是 `dist/index.html`
- [ ] 统一本地启动脚本
- [ ] 清理过时文件和误导性入口
- [ ] 补充版本发布说明
- [ ] 说明本地存储键变更与兼容策略

交付结果：

- 新用户拿到项目后能直接知道怎么运行
- 老用户升级后不会轻易丢配置

## Phase 6. 体验改进

- [ ] 统一所有分页的视觉语言
- [ ] 统一提示文案与错误反馈格式
- [ ] 补充空状态和引导文案
- [ ] 优化移动端和窄屏体验
- [ ] 视情况补充导入导出能力

交付结果：

- 产品体验一致
- 后续继续迭代时成本更低

## 建议优先级

P0：

- 选定唯一主实现
- 统一入口、测试、发布链

P1：

- 迁移或整理核心业务能力
- 建立真实测试

P2：

- 优化体验
- 增加附加能力
