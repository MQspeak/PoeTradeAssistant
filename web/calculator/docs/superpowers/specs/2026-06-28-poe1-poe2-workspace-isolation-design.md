# POE1 / POE2 套利工作区隔离设计

## 目标

在套利网页最顶部增加 POE1 / POE2 高层级切换器。两个游戏共用页面功能和数据结构，但所有配置、价格参数及编辑上下文完全独立。桌面 OCR/自动化程序及其 `profile.json` 不在本次范围内。

## 用户体验

- 切换器位于现有标题、说明和全部功能分页之上。
- 切换器使用两个并列按钮：`POE 1` 与 `POE 2`。
- 当前游戏必须有明显选中态，标题区域同步显示当前游戏。
- 切换时不弹确认框；当前输入即时保存，目标游戏工作区立即恢复。
- 每个游戏独立记住上次所在分页及选中的套利模式。
- 应用记住最后选择的游戏，刷新或重新打开后自动恢复。

## 状态架构

新的顶层持久化状态结构为：

```text
activeGame: "poe1" | "poe2"
games:
  poe1: GameState
  poe2: GameState
```

`GameState` 沿用当前套利网页的完整状态结构，并独立包含：

- 当前分页
- 当前套利模式
- 物品列表
- 基础交易对
- 标的与多币种价格
- 符文套利参数及价格
- 公式套利草稿
- 已保存公式

页面渲染、计算、编辑、保存、导入和重置只能访问 `games[activeGame]`。两个游戏只共享程序代码和数据结构，不共享业务数据对象。

## 持久化与迁移

- 使用新的版本化 localStorage 键保存双游戏顶层状态。
- 优先读取新的双游戏存储。
- 若新存储不存在，但旧键 `poe2-arbitrage-tool-standalone-v3` 中存在有效数据，则将其迁入 `games.poe2`。
- POE1 首次进入时使用新的默认状态。
- 迁移成功后立即写入新存储，后续均以新存储为准。
- 每个游戏在读取时独立执行状态归一化，补齐缺失字段。
- 某个游戏的状态损坏时，该游戏回退到默认状态，不应破坏另一个游戏的有效状态。
- 不删除旧存储键，以保留降级恢复余地；新版本不再向旧键写入。

## 数据流

1. 启动时加载并归一化顶层状态，必要时迁移旧 POE2 数据。
2. 将 `games[activeGame]` 作为当前工作状态交给现有渲染和计算逻辑。
3. 用户修改任何字段时，仅更新当前游戏状态并保存整个顶层状态。
4. 用户切换游戏时，先保存当前工作区，再更改 `activeGame`，然后重新渲染目标工作区。
5. 价格 JSON 导入只更新当前游戏的物品、交易对或价格数据。
6. 重置类操作只重置当前游戏，不改变另一个游戏的数据。

## UI 设计

- 在现有主容器顶部增加独立的游戏选择区域，其视觉层级高于功能分页。
- 两个游戏按钮均显示完整名称，避免只使用含义不明的缩写。
- 选中按钮使用高对比背景、边框及文字颜色；未选中按钮保持可点击但视觉弱化。
- 在现有 Hero 标题或副标题中显示当前游戏名称，形成第二重上下文提示。
- 在窄屏下切换器仍保持两个等宽按钮，不出现横向溢出。

## 容错

- 顶层 JSON 无法解析时，从两个默认游戏状态启动。
- 单个游戏结构不完整时，对该游戏补默认字段。
- 旧 POE2 状态无法解析时，POE2 回退到默认状态，POE1 仍正常初始化。
- 无效的 `activeGame` 回退为 `poe2`，以符合现有用户数据归属。
- 切换操作不得复制、合并或引用另一个游戏的数组与嵌套对象。

## 测试与验收

- 旧键中的现有数据首次启动后完整出现在 POE2，POE1 使用默认数据。
- POE1 和 POE2 的物品、基础交易对、标的价格、符文参数、公式草稿及已保存公式互不影响。
- 两个游戏分别保留自己的当前分页和套利模式。
- 刷新页面后恢复最后选择的游戏及其完整状态。
- 快速来回切换不会丢失已输入内容。
- 价格 JSON 导入只影响当前游戏。
- 重置操作只影响当前游戏。
- 现有套利计算结果与改造前一致。
- 顶部切换器在桌面和窄屏下均清晰可用。
- 所有现有静态测试继续通过，并增加覆盖双游戏存储、迁移和隔离行为的测试。

## 非目标

- 不修改桌面 OCR/自动化程序。
- 不隔离或迁移桌面端 `profile.json`。
- 不为 POE1 或 POE2 增加专属分页、字段或计算规则。
- 不改变现有价格 JSON 文件格式。
