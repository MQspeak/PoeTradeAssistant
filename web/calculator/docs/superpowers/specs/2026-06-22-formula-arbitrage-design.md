# 公式套利分页设计

## 背景

现有工具已经支持物品列表、基础交易对、套利标的和符文套利。现在需要新增一个独立的“公式套利”分页，让玩家可以像搭积木一样定义任意成本项和收益项，并复用已有币种与汇率数据，实时得到收益率、总成本、纯利润和每 D 金币效率。

本设计基于现有单文件应用 `index.html` 的状态管理、事件分发和实时重渲染模式扩展，不引入新的框架层。

## 目标

新增一个“公式套利”分页，支持：

1. 在页面上半区编辑一条公式。
2. 公式包含名称、成本项列表、收益项列表。
3. 成本项和收益项都允许 1 到 10 条。
4. 每条项目支持自由命名、选择币种、填写单价、填写单个金币消耗、填写数量。
5. 自动计算总成本、总收益、纯利润、收益率、每 D 金币效率。
6. 点击保存后将公式存入下方列表。
7. 列表支持点击编辑，将已保存公式回填到上方容器继续修改并再次保存。
8. 当物品列表或基础交易对发生变化时，该分页所有结果实时刷新。

## 非目标

本次不包含以下能力：

1. 不做公式分组、排序、筛选。
2. 不做导入导出。
3. 不做删除确认弹窗以外的复杂交互。
4. 不允许玩家手动指定结算币种。

## 页面结构

新增第五个分页“公式套利”，位于“符文套利”之后。

页面分为两个主容器：

### 公式容器

用于编辑当前公式，包含：

1. 公式名输入框。
2. 成本卡片区。
3. 收益卡片区。
4. 汇总结果区。
5. 保存按钮。
6. 当前是否为“编辑已有公式”的提示。

成本卡片区与收益卡片区都采用可增减条目的卡片列表展示。每个列表至少保留 1 条，最多允许 10 条。

### 公式列表容器

用于展示已保存公式，每行显示：

1. 公式名。
2. 收益率。
3. 纯利润。
4. 金币兑换效率。
5. 编辑按钮。

如果当前保存公式因为缺少交易对而无法计算，则列表中对应列显示提示文本，而不是展示过期缓存结果。

## 数据模型

沿用当前 `state` 持久化结构，新增 `formulaArbitrage` 节点：

```text
formulaArbitrage: {
  draft: {
    editingFormulaId: string,
    name: string,
    costItems: FormulaEntry[],
    revenueItems: FormulaEntry[]
  },
  formulas: FormulaRecord[]
}
```

条目结构：

```text
FormulaEntry: {
  id: string,
  label: string,
  currencyId: string,
  unitPrice: string,
  goldCostPerUnit: string,
  quantity: string
}
```

已保存公式结构：

```text
FormulaRecord: {
  id: string,
  name: string,
  costItems: FormulaEntry[],
  revenueItems: FormulaEntry[]
}
```

说明：

1. 草稿区和已保存公式都保存原始字符串，保持与当前页面输入体验一致。
2. 不额外保存收益率、利润等派生值，所有列表展示都在渲染阶段实时计算。
3. 结算币种不单独存储，统一以“第一条收益项的币种”为准。

## 计算规则

### 结算币种

1. 默认取第一条收益项的 `currencyId` 作为结算币种。
2. 如果第一条收益项没有选择币种，则公式整体视为未完成，提示先补全第一条收益项币种。

### 单条项目价值

每条成本项或收益项的总价值计算为：

`单价 × 数量`

每条项目的总金币消耗计算为：

`单个金币消耗 × 数量`

### 总成本与总收益

1. 成本项：将每条成本项总价值通过基础交易对换算到结算币种后求和。
2. 收益项：将每条收益项总价值通过基础交易对换算到结算币种后求和。
3. 如果某条项目本身已使用结算币种，则直接计入，不需要汇率换算。
4. 如果某条项目缺少通往结算币种的基础交易对，则整条公式返回缺失汇率提示。

### 纯利润与收益率

纯利润：

`总收益 - 总成本`

收益率：

`((总收益 / 总成本) * 100) - 100`

前提是总成本必须大于 0，否则返回未完成提示。

### 金币效率

金币效率继续沿用“每获得 1 个 D 需要消耗多少金币”的口径：

1. 公式总金币消耗 = 所有成本项金币总和 + 所有收益项金币总和。
2. 将纯利润从结算币种换算到 D。
3. 如果纯利润对应 D 数量大于 0，则：

`金币效率 = 公式总金币消耗 / 纯利润对应的 D 数量`

4. 如果缺少 D 币种，提示先在物品列表新增 D。
5. 如果缺少 `结算币种 -> D` 的基础交易对，提示先去基础交易对列表补充。
6. 如果纯利润不为正，不计算金币效率，只展示说明。

## 校验与提示

### 输入校验

每条项目需要校验：

1. 名称非空。
2. 币种已选择。
3. 单价为有效正数。
4. 数量为有效正数。
5. 金币消耗为有效非负数。

### 缺失汇率提示

当某条项目无法换算到结算币种时，提示：

`缺少 X -> 结算币种 的基础交易对，请先去基础交易对列表构建交易对。`

当结算币种无法换算到 D 时，提示：

`当前结算币种缺少与 D 的基础交易对，请先去基础交易对列表构建交易对。`

### 空状态

1. 没有任何币种时，分页显示空状态，引导先去物品列表新增币种。
2. 没有已保存公式时，列表区展示空状态说明。

## 编辑与保存流程

### 新建

1. 进入分页时默认载入一份空草稿。
2. 空草稿包含 1 条成本项和 1 条收益项。

### 保存

1. 当草稿未绑定 `editingFormulaId` 时，保存为新公式。
2. 当草稿绑定 `editingFormulaId` 时，保存覆盖对应公式。
3. 保存后保留当前草稿内容，方便继续微调。

### 编辑

1. 点击列表“编辑”按钮。
2. 将对应公式完整复制到草稿区。
3. 记录 `editingFormulaId`，页面提示当前处于编辑模式。

## 实时联动

以下变化都会触发公式套利页重算：

1. 当前分页内任意字段变动。
2. 物品列表中的币种名称或金币消耗变动。
3. 基础交易对中的汇率变动。
4. 币种被删除，导致公式引用项失效。

实现方式沿用当前全量 `render()` 机制，不做局部计算缓存。

## 实现拆分

### 状态与序列化

1. 扩展默认状态。
2. 扩展本地存储读取与回填。
3. 扩展分页切换枚举。

### 计算层

1. 新增公式条目标准化与校验函数。
2. 新增公式汇总计算函数。
3. 复用现有币种换算和金币效率辅助函数。

### 视图层

1. 新增“公式套利”分页渲染函数。
2. 新增公式编辑卡片渲染。
3. 新增公式列表渲染。

### 事件层

1. 新增公式条目增删。
2. 新增草稿字段编辑。
3. 新增保存。
4. 新增列表编辑。

## 测试策略

现有项目使用 `scripts/*.test.mjs` 通过静态断言检查生成页面结构。本次继续沿用该方式，至少补充：

1. 新分页按钮存在，且位于“符文套利”之后。
2. 状态中存在 `formulaArbitrage` 草稿与列表结构。
3. 存在公式套利计算函数。
4. 页面中存在公式容器与公式列表容器。
5. 页面中存在保存、编辑、成本项、收益项相关文案。
6. 计算逻辑中使用第一条收益项币种作为结算币种。
7. 缺失交易对时存在明确提示文案。

## 风险与约束

1. 当前项目是单文件应用，新增一整页后 `index.html` 会继续膨胀，修改时需要特别注意局部函数边界。
2. 项目目录当前看起来不是标准 Git 仓库根目录，可能无法按常规流程提交设计文档 commit。
3. 现有测试是结构性断言，不会真正执行浏览器交互，因此实现时要尽量让函数名、文案和状态结构稳定、可检索。
